## 1. PROJECT OBJECTIVE

The objective of this challenge is to build a deterministic AI financial agent that evaluates user payment requests (e.g. "Can I afford this laptop?") and determines financial affordability, payment safety, and optimal payment methods.

For every request in `dataset/requests.csv`, the engine calculates:
- `amount_safe_to_pay`: Maximum safe payment on the request date before optional spending changes.
- `affordability_status`: Affordability state (`affordable_now`, `affordable_with_plan`, `affordable_later`, `not_affordable`).
- `recommended_payment_method`: Recommended payment method (`full_payment`, `partial_payment`, `installments`, `wait`, `not_recommended`).
- `payment_plan`: Chronological payment schedule (`<YYYY-MM-DD>:<amount>`).
- `earliest_date_for_full_payment`: Earliest safe date for paying the full requested amount.
- `spending_changes_needed`: Flexible spending adjustments required (`stop:<event_id>` or `reduce_to:<event_id>:<amount>`).
- `decision_explanation`: Concise, factual financial reasoning.

The engine must process all 250 evaluation requests and output predictions to `output.csv`.

## 3. PHASE 1 — FINANCIAL ANALYSIS ENGINE

The Phase 1 core financial analysis engine was constructed to model the user's 90-day cashflow trajectory:
- **Data Loading**: Reads user profiles, transaction events, messages, payment options, and dated exchange rates.
- **Image Evidence Integration**: Transcribes missing event amounts from PNG images (e.g. `event_253` -> 4,365,000 IDR).
- **Foreign Currency Normalization**: Converts non-home currency transactions to home currency using fixed, dated rates.
- **Message Lifecycle Amendments**: Extracts payroll updates (salary amounts/dates), contract terminations, and rent increases from message evidence.
- **Event Status Filtering**: Excludes failed, cancelled, unrealized events, pending credits, and unconfirmed refunds from the forecast.
- **Recurring Cash-Flow Analysis**: Detects historical salary income patterns and recurring contractual obligations (rent, utilities, insurance, education, debt repayments, subscriptions).
- **Duplicate Prevention**: Prevents double-counting between inferred recurrences and explicit future scheduled events.
- **90-Day Timeline Simulation**: Simulates daily available balance over 90 days, asserting that the balance never drops below `minimum_balance_to_keep`.

Key Principle: Historical discretionary spending (e.g. sporadic coffee or dining out) is not automatically replayed as a fixed future obligation, ensuring conservative and realistic financial forecasts.

==================================================

## 4. PHASE 2 — PAYMENT DECISION ENGINE

Built the decision layer on top of the Phase 1 cashflow timeline:
- **`amount_safe_to_pay`**: Derived from baseline financial analysis on `request_date` before optional spending changes, maintaining minimum balance across 90 days, capped at `requested_amount`.
- **`earliest_date_for_full_payment`**: Evaluated independently as the first date in `[request_date, request_date + 90 days]` where paying `requested_amount` in full passes the safety check.
- **Payment Method Eligibility**: Respects user-specified allowed methods (`payment_methods_user_will_consider`) and installment duration limits (`max_installment_months`).
- **Installment Validation**: Evaluates supplied installment offers from `request_payment_options.csv` against the 90-day cashflow timeline.
- **Partial Payment Rules**: Implements the exact 2-payment structure (`(request_date, safe_amount)` and `(earliest_date_for_full_payment, remaining)`) when permitted.
- **WAIT Logic**: Recommends `wait` with status `affordable_later` when full payment becomes safe on or before `desired_completion_date`.
- **Flexible Spending Changes**: Evaluates stoppable/reducible recurring debits matching user preferences, enforcing mutual exclusivity per event (`stop:<event_id>` or `reduce_to:<event_id>:<amount>`).
- **Plan Ranking**: Applies exact challenge ordering:
  1. Complete by `desired_completion_date`
  2. Require fewer/no spending changes
  3. Minimize total amount paid
  4. Start earlier
  5. Fewer payments
  6. Lowest `payment_option_id`

## 5. PHASE 3 — DIAGNOSTICS AND DEBUGGING

Established systematic diagnostic tools and regression testing:
- **Public Sample Diagnostic Tool**: Created `code/diagnose_samples.py` generating `evaluation/sample_diagnostics.csv`, `evaluation/sample_cashflow_trace.csv`, and `evaluation/sample_snapshot_trace.csv`.
- **Salary Pattern Generalization**: Identified that salary descriptions varied across paystubs (e.g. *"Payroll before leave"* vs *"Payroll after returning from leave"*) or had sparse history. Refined salary pattern grouping by category `salary` and direction `credit` to preserve 90-day salary forecasting.
- **Candidate Spending Change Search**: Expanded `change_sets()` to evaluate all flexible debit events (`stoppable`, `reducible`) matching user preferences.
- **Regression Protection**: Verified that core financial logic remained general without hardcoding any request IDs or sample answers.

Major Lessons:
- Discretionary variable spending should not be treated as fixed contractual debt.
- Unconfirmed variable income (commissions, unapproved bonuses) must not be treated as guaranteed future cashflows.
- Baseline `amount_safe_to_pay` must remain independent of optional spending changes.

## 10. KEY TECHNICAL DECISIONS

1. Explicit future events take precedence over inferred recurrences to prevent double-counting.
2. Historical discretionary spending (dining out, shopping) is not treated as a fixed contractual debt.
3. Unconfirmed/variable income (commissions, bonuses) is excluded from guaranteed recurring income.
4. All candidate payment options are validated against chronological 90-day balance trajectories.
5. Minimum balance floor is enforced across all 90 forecast days.
6. Baseline `amount_safe_to_pay` is evaluated before optional spending changes.
7. Safe candidate plans are ranked by deadline completion, spending changes, total cost, start date, payment count, and option ID.
